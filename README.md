# 微信 AI 自动回复

这是一个基于 Windows UI Automation、DeepSeek 兼容 API 和 Tkinter 的微信自动回复工具。它可以读取当前微信聊天窗口中的新消息，根据最近对话、风格样本、联系人关系和语气模式生成回复，并模拟阅读、思考、打字和分段发送的过程。

工具适合个人测试和辅助回复。正式开启自动发送前，建议先使用“测试回复（不发送）”观察生成结果，并只对一个联系人进行小范围验证。

## 功能概览

- 通过 DeepSeek/OpenAI 兼容接口生成中文聊天回复。
- 根据最近对话判断话题、情绪和回复必要性。
- 从自己的聊天记录中提取句长、标点、常用表达和回复节奏。
- 在样本进入模型前清理 URL、API Key、验证码、长数字和远程协助信息。
- 为联系人设置关系和语气模式：普通朋友、亲近朋友、家人、工作关系等。
- 支持自然、口语、轻松接梗和保守克制等回复模式。
- 支持群聊：只对群聊名单中的群启用自动回复，且默认仅在被 @ 时回复。
- 本地缓存每个联系人的深层上下文（最多 300 条）；有缓存时启动只同步当前屏幕，不重复翻页。
- 模拟阅读延迟、打字速度、深夜模式和多条消息之间的间隔。
- 支持 `<NO_REPLY>` 和 `<MSG_SPLIT>` 内部标记。
- 支持测试生成结果、预览消息拆分和预计打字时间，测试过程不会发送微信消息。
- 提供始终置顶的悬浮控制窗，可快速查看监听状态、切换自动发送和打开主窗口。
- API Key 不写入 `config.json`；未使用环境变量时，会用 Windows DPAPI 加密保存在本机 `secrets.json`。日志会对 URL、密钥和长数字进行脱敏。

## 环境要求

- Windows。
- Python 3.10 或更高版本，建议使用项目实际运行的 Python 3.13 环境。
- 已登录的微信 4.x 桌面客户端。
- 可访问 DeepSeek API 或其他 OpenAI 兼容 API 服务。
- 微信窗口需要保持可被 UI Automation 访问，首次连接时不要最小化窗口。

## 安装依赖

在项目根目录执行：

```powershell
python -m pip install -r requirements.txt
```

依赖包括：

- `openai`：调用 DeepSeek/OpenAI 兼容接口。
- `pywin32`：通过 Windows API 操作微信窗口（查找/恢复/置前）并读写剪贴板。
- `uiautomation`：基于 Windows UI Automation 读取微信聊天窗口中的控件和消息。
- `Pillow`：截取微信窗口区域用于界面定位与消息读取。

## 配置 API Key

推荐使用环境变量。PowerShell 当前窗口配置方式：

```powershell
$env:DEEPSEEK_API_KEY = "你的新 API Key"
```

然后在同一个窗口启动程序：

```powershell
python main.py
```

环境变量只对当前 PowerShell 窗口有效。若需要长期配置，可以在 Windows 用户环境变量中添加 `DEEPSEEK_API_KEY`，然后重新打开终端。

如果不想每次设置环境变量，也可以直接在设置页填入 Key 并点击“保存设置”。程序会用 Windows DPAPI 加密后写入本机 `secrets.json`，只有当前 Windows 用户能解密，重启后自动恢复。环境变量的优先级高于本地保存的 Key。

### 自定义接口地址与模型

设置页的“AI 接口配置”还可以修改：

- `API 地址`：任意 OpenAI 兼容服务的地址，例如 `https://api.deepseek.com`。
- `模型`：可直接输入模型名，或点击“拉取模型”从服务的 `/models` 接口获取列表后选择。
- `温度` / `最大 tokens`：控制回复随机性和单次生成长度。

修改后点击“保存设置”生效。若服务商不支持 `/models` 接口，手动填写模型名即可。

不要把真实 API Key 写进以下位置：

- `config.json`。
- 聊天记录或风格样本。
- 截图、日志、测试代码或 Git 提交。
- 任何需要分享或提交的 `secrets.json`（本机加密文件，已被 `.gitignore` 忽略）。

项目启动时会自动清理旧配置中的 API Key 字段和敏感风格样本。已经暴露过的 Key 仍然应在服务商后台撤销并重新生成，单纯从本地文件删除并不等于撤销旧密钥。

## 启动程序

确保微信已经登录后执行：

```powershell
python main.py
```

启动后会打开“微信 AI 自动回复”窗口。程序不会自动连接或发送，必须在界面中手动点击“开启自动监听”。

程序同时显示一个小型悬浮控制窗。悬浮窗默认置顶，可以拖动到合适位置；关闭悬浮窗只会隐藏它，不会停止监听。需要恢复时，可以从主窗口的控制台重新打开，或重启程序。悬浮窗中的“打开主窗口”只恢复主界面，不改变监听状态。

## 首次使用流程

### 1. 配置联系人

进入设置页，在“目标联系人”中添加允许自动回复的联系人。程序只会对列表中的联系人执行自动回复。

选中联系人后，可以配置：

- `unknown`：关系未知，使用保守的自然语气。
- `friend`：普通朋友。
- `close_friend`：亲近朋友，可以使用更多轻度调侃。
- `family`：家人，减少网络梗和过度互怼。
- `work`：工作关系，保持清楚、简洁和克制。

语气模式包括：

- `natural`：自然平衡。
- `casual`：更口语、更简短。
- `playful`：允许更多接梗和轻度调侃。
- `conservative`：减少俚语、脏话和主动延伸。

### 2. 导入风格样本

进入风格学习页，可以：

- 导入文本聊天记录。
- 从当前微信聊天抓取自己的历史文本消息。
- 清空已有样本。

建议使用自己真实发送过的消息，覆盖日常闲聊、提问、吐槽、工作沟通和结束话题等多种场景。样本越单一，生成结果越容易固定化。

程序会在保存和构建 prompt 前进行脱敏，但仍建议不要主动导入包含密钥、密码、身份证号、手机号、验证码或远程控制信息的文件。

### 3. 生成人设画像

设置页中的“AI 生成人设”和“优化人设”会根据风格样本生成可编辑的风格画像。画像主要描述：

- 性格倾向。
- 回复节奏和句子长短。
- 接梗、反问、吐槽和安慰等互动方式。
- 常见表达及其适用场景。
- 标点、换行和表情习惯。
- 亲近关系和普通关系之间的表达边界。

生成后请人工检查，再点击“保存设置”。程序不会自动把生成结果直接当成最终配置。

### 4. 测试回复

在设置页点击“测试回复（不发送）”：

1. 选择联系人。
2. 选择关系和语气模式。
3. 输入一条模拟收到的消息。
4. 点击“生成预览”。

窗口会显示回复内容、消息分段和预计打字时间。这个流程只调用 AI，不连接发送流程，不会向微信发送消息。

### 5. 小范围启动

确认结果符合预期后：

1. 在微信中打开目标联系人聊天。
2. 确认该联系人已经加入自动回复列表。
3. 在控制台点击“开启自动监听”。
4. 确认“自动发送回复”开关的状态：
   - 关闭：监听消息、生成回复，并将回复填入“主动发消息”的消息框，但不会发送。
   - 开启：监听消息、生成回复，并按照阅读/打字延迟自动发送。
5. 关闭自动发送时，可以在消息框人工检查后点击“发送”。
6. 不需要继续监听时点击“停止自动监听”。

监听和发送是两个独立开关。运行监听不会自动打开自动发送；默认配置为关闭自动发送，避免测试时误发消息。

## 群聊使用

群聊默认采用“仅被 @ 时回复”的策略：

1. 进入设置页的“群聊设置”。
2. 在群聊列表中添加群名称，名称需要与微信聊天窗口标题一致。
3. 填写“我的群昵称”，即别人 @ 你时显示的名字；不同群里昵称不同时，用逗号分隔，例如 `小王, 王哥`。
4. 保持“群里仅被 @ 时回复”勾选，点击“保存设置”。

开启监听后：

- 群聊列表中的群，只有消息文本包含 `@你的群昵称` 才会生成回复。
- 未被 @ 的群消息只写入本地上下文，不会触发回复，也不会写入持久化历史。
- 单聊行为保持不变；不在群聊列表中的聊天按单聊处理。

限制：微信 4.x 的 UI Automation 不提供稳定的群成员发送者信息，程序依据消息文本中的 @昵称 判断。若群里 @ 你时显示的名字与配置不一致，请更新“我的群昵称”。建议先在目标群发一条 @ 消息验证。若群昵称留空，群消息会被跳过，并在控制台提示。

## 上下文缓存

程序会把见过的聊天上下文缓存到项目根目录的 `context_cache.json`，每个联系人最多保留 300 条（只是本地上下文，不是完整聊天备份）。

- 第一次遇到某个聊天时，会做一次深度回看（最多 30 页 / 300 条），然后写入缓存。
- 之后启动监听或切回该聊天，只读取当前屏幕可见的消息做增量同步，**不再向上翻页**。
- 设置页“目标联系人”里的“深度缓存当前聊天”可以手动重新深度抓取当前聊天（需要先停止监听）。
- 发给模型的上下文仍然是设置页的“上下文条数”（默认 30）；想让它看更多可以调高。缓存条数只影响本地存档深度，不直接决定每轮 prompt 的大小。
- 如果你正在微信输入框打字，深度回看会被跳过，避免抢焦点。
- `context_cache.json` 含聊天内容，已被 `.gitignore` 忽略，不要提交或分享。

## 界面说明

### 主动发消息

可以选择联系人并手动发送消息，也可以让 AI 根据历史语境生成一条草稿。AI 草稿会填入编辑框，仍需要用户确认后才会发送。

### 对话记录

显示本地保存的联系人上下文。上下文用于帮助模型理解最近话题，不代表完整的微信聊天备份。

### 风格学习

负责导入、抓取、清理和预览风格样本。风格预览显示统计特征，不等于模型会在每条消息中强制使用所有高频词。

### 设置

包括 API 配置、联系人关系、风格画像、延迟参数、上下文条数、深夜模式和保守回复模式。

### 控制台

显示连接状态、收到的消息、AI 判断、发送结果和错误信息。控制台中的“开启自动监听”只控制消息监听线程；“自动发送回复”单独控制是否调用微信发送接口。日志中的 URL、密钥和长数字会被替换为 `[已脱敏]`，但仍不建议把日志公开发布。

悬浮控制窗提供同样的两个高频操作：开启/停止监听，以及开启/关闭自动发送。它适合把主窗口最小化或切换到其他窗口时快速查看状态。

## 回复处理逻辑

收到新消息后，大致按以下顺序处理：

1. 判断是否来自自己，避免回复自己的消息。
2. 读取或刷新最近聊天上下文。
3. 保存收到的用户消息。
4. 跳过纯确认、单字表情或明显无需回复的消息。
5. 根据不回复概率和上下文决定是否忽略。
6. 根据消息长度、疑问特征、深夜模式计算阅读延迟。
7. 将联系人画像、风格画像和最近上下文发送给模型。
8. 清理并检查模型输出，必要时最多重试一次。
9. 根据 `<MSG_SPLIT>` 或中文句末标点拆分消息。
10. 模拟打字并逐段发送。
11. 只有微信实际发送成功的内容才会写入 assistant 对话历史。

如果 API 调用失败、程序停止或微信发送失败，未成功发送的内容不会被标记为已发送。若多段消息只有部分发送成功，历史中只保留成功部分。

## 配置文件

`config.json` 是运行时配置和本地上下文文件，首次启动或保存设置时会自动创建。字段示例见 [config.example.json](config.example.json)。

`config.json` 已被 `.gitignore` 忽略，且其中保存了本地聊天上下文，不要提交到仓库。

主要字段：

| 字段 | 说明 |
| --- | --- |
| `api_base` | OpenAI 兼容 API 地址 |
| `model` | 使用的模型名称 |
| `temperature` | 回复随机性，数值越高越发散 |
| `max_tokens` | 单次生成的最大 token 数；推理模型建议 800 以上 |
| `contacts` | 允许自动回复的联系人列表 |
| `group_chats` | 群聊名单，默认仅被 @ 时回复 |
| `my_group_nickname` | 群里的 @ 昵称，多个用逗号分隔 |
| `group_reply_on_mention_only` | 群聊是否仅在被 @ 时回复 |
| `contact_profiles` | 联系人的关系、语气和备注 |
| `persona` | 可编辑的风格画像 |
| `conservative_mode` | 是否减少俚语、脏话和主动延伸 |
| `auto_send_replies` | 是否自动发送生成的回复，默认关闭 |
| `read_delay_min/max` | 阅读和思考延迟范围 |
| `typing_speed_min/max` | 每个字符的模拟打字时间 |
| `no_reply_probability` | 随机忽略消息的概率 |
| `night_mode` | 深夜时增加延迟并降低回复倾向 |
| `context_length` | 保存和发送给模型的上下文条数 |
| `style_samples` | 风格学习样本，保存时会进行脱敏 |
| `conversations` | 按联系人保存的本地对话上下文 |

不要手动将 `api_key` 写入 `config.json`。程序保存配置时会把这个字段清空；未使用环境变量时，Key 会单独加密保存在同目录的 `secrets.json`。

## 常见问题

### 提示未设置 API Key

确认在启动程序的同一个 PowerShell 窗口中设置了环境变量：

```powershell
$env:DEEPSEEK_API_KEY = "你的新 API Key"
python main.py
```

也可以在设置页临时输入，但未通过环境变量配置时，程序重启后不会从 `config.json` 恢复这个 Key。

### 找不到微信窗口

确认微信 4.x 已登录、窗口没有被关闭，并先恢复窗口后再点击启动。某些情况下需要以相同权限运行微信和 Python 程序。

### 能连接微信但读取不到消息

确认当前打开的是聊天窗口而不是其他页面。UI Automation 依赖微信当前界面结构，微信版本更新后可能需要调整控件定位逻辑。

### 日志显示“AI 判断无需回复 (empty_content)”

说明模型把 token 预算用在了隐藏的思考内容上，最终回答为空。把设置页的“最大 tokens”调到 800 以上即可；程序遇到空内容也会自动加大预算重试一次。如果日志显示 `(no_reply_marker)`，才是模型明确判断这条消息不需要回复。

### 回复太机械

增加多场景风格样本，减少 persona 中对固定口头禅的描述，并尝试：

- 为联系人选择正确的关系。
- 使用 `natural` 或 `conservative` 模式对比。
- 在测试回复窗口中用同一消息多次测试。
- 检查最近对话上下文是否真实、连续。

### 回复太慢或太快

在设置页调整阅读延迟和打字速度范围。深夜模式、长消息、问句和多段消息都会影响总延迟。

### 测试没有运行

优先使用项目自带的 `unittest` 命令。若执行 `pytest` 报 `No module named pytest`，说明当前 Python 环境没有安装 pytest，这不影响 `unittest` 测试。

## 安全与使用边界

- 只对自己拥有或明确获准操作的微信账号和联系人使用。
- 自动发送前先使用测试回复预览，并从单个联系人开始验证。
- 不要导入包含 API Key、密码、验证码、身份证号、支付信息或远程控制信息的聊天记录。
- 不要把 `config.json`、`context_cache.json`、日志、截图和完整聊天样本上传到公共仓库。
- 任何已经暴露过的 API Key 都应在服务商后台撤销，不要只依赖本地删除。
- 工具会尽量生成自然、符合上下文的回复，但不会保证模型始终理解事实、关系或玩笑。重要消息应由用户人工确认。

core/context_cache.py       上下文缓存读写和裁剪
